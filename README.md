# Sales Manager FIRST — F1-09 R1

Сборщик структурированного контекста передачи диалога менеджеру. Учебное практическое задание Дмитрия Степанова, выполненное 12–13 октября 2026 года.

**Статус:** реализация подготовлена, 27 новых тестов прошли. Независимая приёмка и интеграция выполняются отдельно. Этот компонент относится к FG10; его выполнение само по себе не закрывает FG10 и не изменяет готовность FIRST.

## Назначение

Модуль получает подготовленный доверенным серверным слоем словарь: область клиента и кампании, историю переписки, факты, материалы, язык, краткое резюме и следующий шаг. Проверяет контракт и возвращает независимую копию со стабильным порядком данных и контрольной суммой.

Функция не определяет заинтересованность клиента, не извлекает договорённости, не переводит текст, не получает историю из БД и не отправляет уведомления. Она сохраняет предоставленные сообщения покупателя, автоматизации и человека при всех допустимых статусах.

## Входной контракт

Все поля обязательны, лишние запрещены. Проверяются точные встроенные dict, list, str и int; bool и подклассы этих типов отвергаются.

| Поля | Правило |
| --- | --- |
| schema_version | FIRST_HANDOFF_INPUT_V1 |
| client_id, runtime_campaign_id, lead_id, mailbox_ref, thread_id | ID области данных |
| handoff_event_id | ID события, назначенный координатором |
| product_id, policy_version | ID продукта и версии политики |
| status | ACTIVE, HANDED_OFF, STOPPED |
| reason | INTEREST, OUT_OF_SCOPE |
| locale, language_pack_version | Выбранный язык и версия |
| language_packs | Непустой реестр языка → версии, без фиксированного максимума числа языков |
| summary, next_step | Непустой текст до 2000 символов |
| history | 1–100 сообщений |
| facts, materials | По 0–50 элементов |

ID — строка 1–128 символов без пробелов по краям и управляющих ASCII-символов. Регистр сохраняется. Текст сохраняется точно; допустимы LF и табуляция, остальные управляющие ASCII-символы запрещены.

Сообщение содержит message_id, пять полей области данных, sequence, direction, actor, body, fact_ids, material_ids. Область каждого сообщения должна совпадать с контекстом. sequence — целое 0–1 000 000 000; ID сообщения и sequence уникальны.

Для INBOUND допустим BUYER, для OUTBOUND — AUTOMATION или HUMAN. body ограничен 20 000 символами. Списки ссылок содержат до 50 уникальных ID и ссылаются на существующие факты или материалы.

Факт: fact_id, text до 2000 символов, source_ref. Материал: material_id, name, evidence_ref. source_ref и evidence_ref — непрозрачные ID; модуль их не открывает.

## Обработка и приоритет ошибок

| Порядок | Проверка | Код |
| --- | --- | --- |
| 1 | Структура всего входа, типы, размеры и допустимые значения | INVALID_CONTEXT |
| 2 | Язык и версия соответствуют реестру | LANGUAGE_SCOPE_MISMATCH |
| 3 | Область данных каждого сообщения | MESSAGE_SCOPE_MISMATCH |
| 4 | Дубли ID, sequence и ссылок | DUPLICATE_ID |
| 5 | Наличие фактов и материалов по ссылкам | REFERENCE_NOT_FOUND |

Весь вход проверяется структурно до следующих этапов. При нескольких дефектах действует этот порядок. Ошибка не включает сырые данные, имена или текст сообщений.

После проверок deepcopy отделяет вложенные словари и списки результата от аргумента. История сортируется по sequence, факты по fact_id, материалы по material_id, ссылки внутри сообщений — по строковому ID в стандартном порядке Python.

## Выход и SHA-256

Результат сохраняет значения входа, заменяет schema_version на FIRST_HANDOFF_CONTEXT_V1 и добавляет:

| Поле | Значение |
| --- | --- |
| handoff_id | Точное значение handoff_event_id |
| content_sha256 | SHA-256 канонического payload |
| delivery_status | NOT_DISPATCHED |

Хеш рассчитывается после сортировки и замены schema_version, **до** добавления трёх служебных полей:

```python
canonical_bytes = json.dumps(
    payload,
    ensure_ascii=False,
    sort_keys=True,
    separators=(",", ":"),
    allow_nan=False,
).encode("utf-8")
content_sha256 = hashlib.sha256(canonical_bytes).hexdigest()
```

Перестановка элементов входных списков не меняет результат. Изменение body при том же событии сохраняет handoff_id и меняет хеш. Это не гарантия однократной доставки: состояние доставки должен вести отдельный диспетчер.

## Тесты и проверенные сценарии

27 методов unittest с дополнительными subTest-проверками охватывают:

- минимальный корректный пример и независимый расчёт хеша;
- сохранение русского и английского текста, дополнительный синтетический язык и реестр более 100 языков;
- неверную локаль и версию, каждое из пяти полей области данных и чужое последнее сообщение;
- отсутствующие и лишние поля, неправильные типы, подклассы, bool вместо sequence;
- границы ID, текста, history, facts, materials и списков ссылок;
- управляющие ASCII-символы, дубликаты, отсутствующие ссылки и неверные пары direction/actor;
- полную предоставленную историю при ACTIVE, HANDED_OFF и STOPPED;
- стабильную сортировку и результат при перестановках;
- смену хеша при изменении body, неизменность входа и независимость вложенных объектов;
- приоритет ошибок при одновременных дефектах.

Синтетические языки и данные проверяют контракт и расширяемость, а не реальную продуктовую поддержку или продажи.

## Границы интеграции

Координатор назначает handoff_event_id и передаёт доверенные summary, next_step и reason. Через явный адаптер product_id получает принятое offer.offer_id; policy_version относится к политике передачи и не заменяется binding_version. Языковые значения берутся из принятого реестра.

Интегратор отвечает за полноту истории из БД, истинность фактов, проверку интереса, смену владельца диалога, остановку автоматических сообщений, уведомление менеджера и надёжную доставку. NOT_DISPATCHED означает отсутствие доставки из этого компонента.

Модуль не использует часы, случайность, окружение, файлы, сеть или БД. Его импорт не запускает внешние действия. macOS-проверка, независимая приёмка и фактическая доставка не подтверждены.
