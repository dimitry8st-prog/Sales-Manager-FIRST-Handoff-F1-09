ТЕХНИЧЕСКОЕ ЗАДАНИЕ F1-09 R1
Дмитрий — стажер
Sales Manager FIRST: сборщик контекста передачи человеку

1. Цель и границы

Создать один небольшой модуль, который собирает структурированный контекст передачи из доверенных серверных данных. Результат содержит всю предоставленную историю, подтверждённые факты и ссылки на материалы. Модуль ничего не придумывает, не переводит, не отправляет и не сохраняет в БД.

Это отдельный компонент этапа FG10. Его приёмка сама по себе не закрывает FG10 и не изменяет индекс готовности FIRST. Проверка заинтересованности клиента, получение полной истории из БД, уведомление человека, остановка автоматических сообщений и надёжная доставка передачи выполняются другими компонентами.

В этой задаче нет отдельного графа договорённостей. Уже подтверждённые договорённости могут входить в переданные факты; модуль не извлекает их из переписки.

2. Разрешённые изменения

Добавить только два файла относительно source/:
- sales_first_handoff.py
- tests/test_first_handoff.py

Исходные файлы, зависимости, конфигурацию, SQL и NO_OUTBOUND не менять. Использовать Python 3.12 и стандартную библиотеку. Не импортировать runtime, store, connectors или новые модули других разработчиков. Не запускать сервер, worker, миграции, Docker или внешние запросы.

3. Точный API

class HandoffContextError(ValueError)
Публичное свойство code содержит строку ошибки; str(exception) возвращает только этот код.

assemble_handoff_context(context: dict) -> dict

Функция чистая: не использует часы, случайность, окружение, файлы, сеть или БД. Она не изменяет аргумент. Изменяемые объекты результата не должны ссылаться на списки или словари аргумента. Одинаковый вход даёт одинаковый результат.

4. Общие правила данных

Все перечисленные поля обязательны. Неизвестные поля запрещены. dict, list, str и int проверяются как точные встроенные типы; bool не считается int.

ID — строка длиной 1–128 символов, без пробелов по краям и без управляющих ASCII-символов U+0000–U+001F и U+007F. Регистр ID сохраняется. UUID не требуется.

Текст — строка длиной 1–20000 символов, не пустая после strip(). В ней разрешены переносы строк и табуляция; другие управляющие ASCII-символы запрещены. Сохранять исходный текст точно: не обрезать, не переводить и не исправлять. Для полей summary и next_step максимум составляет 2000 символов.

5. Входной контракт

context — словарь ровно со следующими полями:
- schema_version: точная строка FIRST_HANDOFF_INPUT_V1;
- client_id, runtime_campaign_id, lead_id, mailbox_ref, thread_id: ID;
- handoff_event_id: ID события передачи, выделенный доверенным координатором;
- product_id, policy_version: ID;
- status: ACTIVE, HANDED_OFF или STOPPED;
- reason: INTEREST или OUT_OF_SCOPE;
- locale, language_pack_version: ID;
- language_packs: непустой словарь ID языка → ID версии; фиксированного максимума количества языков нет;
- summary, next_step: текст максимум 2000 символов;
- history: список из 1–100 сообщений;
- facts: список из 0–50 фактов;
- materials: список из 0–50 материалов.

locale должен присутствовать в language_packs, а его версия должна точно совпадать с language_pack_version. Не зашивать список языков в код. Начальные тестовые языки FIRST — en-GB и ru-RU; дополнительный синтетический язык и реестр более чем из 100 синтетических языков проверяют расширяемость, но не означает его реальную продуктовую поддержку.

Граница интеграции: context.product_id получает значение принятого offer.offer_id через явный адаптер координатора. policy_version — версия политики передачи; она не подменяется binding_version предложения. language_packs и выбранные locale/language_pack_version адаптер получает из принятого языкового реестра. Различие названий полей других задач не требует их импорта или изменения в этой работе.

summary, next_step и reason уже подготовлены доверенным слоем. Модуль копирует их, но не доказывает правдивость и не определяет заинтересованность клиента по тексту письма.

Каждое сообщение history имеет ровно:
- message_id: ID;
- client_id, runtime_campaign_id, lead_id, mailbox_ref, thread_id: ID;
- sequence: int от 0 до 1000000000;
- direction: INBOUND или OUTBOUND;
- actor: BUYER, AUTOMATION или HUMAN;
- body: текст;
- fact_ids: список из 0–50 ID без повторов;
- material_ids: список из 0–50 ID без повторов.

Все пять полей области данных сообщения должны совпадать с context. Для INBOUND actor обязан быть BUYER; для OUTBOUND — AUTOMATION или HUMAN. message_id и sequence должны быть уникальны в истории. sequence — уже установленный сервером порядок сохранения: функция не разбирает даты и не восстанавливает порядок самостоятельно.

Каждый факт facts имеет ровно:
- fact_id: ID;
- text: текст максимум 2000 символов;
- source_ref: ID доказательства.

Каждый материал materials имеет ровно:
- material_id: ID;
- name: ID;
- evidence_ref: ID доказательства.

fact_id и material_id уникальны внутри своих списков. Все ссылки из message.fact_ids должны существовать в facts, а из message.material_ids — в materials. source_ref и evidence_ref — непрозрачные идентификаторы: не открывать их как URL и не скачивать файлы.

Не удалять сообщения при status=HANDED_OFF или STOPPED. Сообщения человека и новые входящие после передачи должны остаться в результате. Полноту истории относительно настоящей БД проверит интегратор: локальная функция может проверить только предоставленный список.

6. Выход и контрольная сумма

Сформировать payload со всеми полями context, но schema_version заменить на FIRST_HANDOFF_CONTEXT_V1.

Привести списки к стабильному порядку:
- history: по sequence по возрастанию;
- facts: по fact_id в стандартном порядке Python для строк;
- materials: по material_id;
- fact_ids и material_ids внутри каждого сообщения: по строковому ID.

Остальные значения сохранять точно. Затем вычислить:
canonical_bytes = json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(',', ':'), allow_nan=False).encode('utf-8')
content_sha256 = hashlib.sha256(canonical_bytes).hexdigest()

Вернуть payload с тремя дополнительными полями:
- handoff_id: точное значение context.handoff_event_id;
- content_sha256: вычисленная контрольная сумма;
- delivery_status: точная строка NOT_DISPATCHED.

handoff_id назначает доверенный координатор, а не этот модуль. Изменение истории при том же событии сохраняет handoff_id и изменяет content_sha256. Это не гарантия однократной доставки: будущий диспетчер должен привязать ID к области данных и хранить состояние операции.

NOT_DISPATCHED означает, что этот компонент не вызывал доставку; он не проверяет историю внешних уведомлений. Функция не меняет ownership, status или расписание follow-up.

7. Ошибки и их порядок

Проверять в следующем порядке:
1) Поля, структура, типы, диапазоны и разрешённые значения всего входа: INVALID_CONTEXT.
2) Связь locale с language_packs: LANGUAGE_SCOPE_MISMATCH.
3) Совпадение области данных каждого сообщения: MESSAGE_SCOPE_MISMATCH.
4) Повторные message_id, sequence, fact_id, material_id или ссылки внутри одного списка: DUPLICATE_ID.
5) Отсутствующие факты или материалы по ссылкам сообщений: REFERENCE_NOT_FOUND.

При нескольких дефектах возвращать исключение с первым кодом согласно этому порядку. Не возвращать частичный результат. Неверные пользовательские структуры не должны выпускать наружу KeyError или TypeError. Код ошибки не содержит имён, адресов, текста сообщений и сырых входных данных.

8. Полный синтетический пример

{"schema_version":"FIRST_HANDOFF_INPUT_V1","client_id":"c-test","runtime_campaign_id":"campaign-test","lead_id":"lead-test","mailbox_ref":"mb-test","thread_id":"thread-test","handoff_event_id":"handoff-test","product_id":"product-test","policy_version":"policy-test","status":"HANDED_OFF","reason":"INTEREST","locale":"ru-RU","language_pack_version":"ru-test-v1","language_packs":{"en-GB":"en-test-v1","ru-RU":"ru-test-v1"},"summary":"Синтетический клиент просит обсудить предложение.","next_step":"Проверить согласованный следующий шаг.","history":[{"message_id":"msg-test","client_id":"c-test","runtime_campaign_id":"campaign-test","lead_id":"lead-test","mailbox_ref":"mb-test","thread_id":"thread-test","sequence":0,"direction":"INBOUND","actor":"BUYER","body":"Синтетический пример: обсудим предложение.","fact_ids":[],"material_ids":[]}],"facts":[],"materials":[]}

Неверный буквальный вход: {} → INVALID_CONTEXT.
Копия полного примера с history[0].mailbox_ref='foreign' → MESSAGE_SCOPE_MISMATCH.
Копия с locale='de-DE' без соответствующего пакета → LANGUAGE_SCOPE_MISMATCH.
Копия с history[0].fact_ids=['missing'] → REFERENCE_NOT_FOUND.

9. Обязательные тесты unittest

- Полный минимальный пример: правильные ключи и значения результата.
- Сохранение английского и русского текста; дополнительный синтетический языковой пакет без изменения кода.
- Неизвестная локаль и несовпадающая версия.
- Несовпадение каждого из пяти полей области данных; чужое сообщение в конце истории также обнаруживается.
- Пропущенные и лишние поля, неправильные типы, bool вместо sequence, границы размеров списков и строк.
- Повторы ID, sequence и ссылок; отсутствующие ссылки.
- Неверные сочетания direction/actor.
- ACTIVE, HANDED_OFF и STOPPED сохраняют все сообщения, включая OUTBOUND/HUMAN.
- Перестановка элементов входных списков не меняет результат.
- Изменение body при прежнем handoff_event_id сохраняет handoff_id и меняет content_sha256.
- Отсутствие изменения входа; изменение возвращённого списка не меняет вход.
- Приоритет ошибок на примере нескольких одновременных дефектов.

Для проверки хеша самостоятельно сформировать ожидаемый payload в тесте и применить описанное правило JSON/SHA256. Не вызывать внутренний helper целевого модуля и не подменять целевую функцию mock. Синтетический пример не выдавать за подтверждённую продажу или внешнюю интеграцию.
